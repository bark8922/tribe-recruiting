TRANSFORMStage 2 — PROD V2 monolith

Config 375145203. 3×/day, ~800 sec wall-clock per run. Structurally 1 block named code with 3 ordered parts (down from 5 after the Phase 2 refactor on 2026-06-08/09 — Part 0 and Part 2 were removed and their outputs replaced with Storage Input from the static bucket out.c-recruitee-static):

PartSizeWhat it does
Part 1 — Bubble data~39 KB88% of all PROD V2 code. Builds tmp_job, final_event (11 LEFT JOINs + ROW_NUMBER window over 14.9M-row Events), final_candidate_stage_bubble (6 sequential UPDATEs — three of them reference the statically-staged RECRUITEE_EVENTS table from Storage Input), final_talent_bubble, final_email, final_talent_position, final_talent_employer, final_screen, final_screen_techstack, final_screen_lang, final_user, final_job_goals.
Part 3 — Final tables~8 KBUnions Bubble + Recruitee → final talent, candidate, event, candidate_stage, client. The Recruitee side comes from Storage Input (out.c-recruitee-static.final_*_recruitee), pre-computed once on 2026-06-08. Each UNION SELECT against a recruitee table uses TRY_TO_BOOLEAN/TRY_TO_DATE casts to convert TEXT columns (Storage Input default) back to BOOLEAN/DATE.
Part 4 — Andy tail432 BBuilds analytic + job_ai_filter.

Phase 2 refactor note (2026-06-09): Original Parts 0 and 2 recomputed frozen Recruitee outputs every PROD V2 run, 3 times daily. Both were removed; pre-computed tables now flow through as Storage Input from out.c-recruitee-static. The static rebuild transformation (01ktkfs2j50hre305cv1w1kqpg) ran once and is idle. Net ~7% runtime saved (~62 sec/run × 3 runs/day × 30 days ≈ 10-15 cr/mo) on top of the larger Phase 0/1 savings. Critical detail for anyone re-touching this: the Storage Input destinations for recruitee_stage and recruitee_events are UPPERCASE because Part 1 references them unquoted (Snowflake auto-uppercases unquoted identifiers); the 4 final_*_recruitee inputs use lowercase because Part 3 references them quoted.

Surprises worth remembering

Revenue 2 was running until 2026-04-14, then went silent

Config 458760018 "Revenue - 2. data prep" is marked enabled=false in Flow B. But its last 10 jobs all ran on 2026-04-13/14 at 5×/day. Someone disabled it. Result: client_cost has been frozen since 2026-04-14 — and PBI has 3 active revenue measures pointing at it. Andy's PBI revenue tiles have been showing 7-week-old data. Either intentional (no one noticed) or oversight.

Action: ask Andy whether this was intentional.

talent_employer is dead even inside PBI

Loaded by Andy's PBIX from out.c-reporting-v2.talent_employer but has 0 relationships, 0 measures, 0 page references. 432K rows / 14 MB materialized every PROD V2 run. Wasted on both sides. Only reason not to drop: Rodrigo's potential Data Download ask.

analytic is renamed to analytic_usage in PBI

PBI's M query aliases the table. Name-only searches for analytic in the PBIX will miss the 2 measures (7 days moving avg, 7 days moving avg limited) that use it.

The Full Bubble extractor is mostly aliases

The "Full" bucket (122491135) holds 42 tables, but the 12 high-traffic ones are aliases pointing back to the Incremental bucket (122527414). When PROD V2 references bubble_Event, the actual data lives in the Incremental bucket. (verified: row counts identical in both)

PROD V2 runs the Events scan twice

Part 1 has a CTAS for final_event with a ROW_NUMBER window over all 14.9M events, then a post-CTAS UPDATE that re-runs the same window. Combined with 11 LEFT JOINs in the CTAS, this is the cost driver. If we ever want to optimize PROD V2, this is where the gain is.

WBR/MBR megatransform is 15 tables in one config

Config 01kpr0tr0… produces 15 output tables — WBR, MBR, TS Summary, IR (6), Sourcing Dashboard (2). Operationally convenient but a single failure breaks every dashboard except Project Dashboard + Time to Hire.
